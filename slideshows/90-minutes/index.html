Section 2 · Anatomy · ★ remember this slide

The opt-in pair

block.json

"supports": { "interactivity": true }

Loads the engine. It enqueues the @wordpress/interactivity runtime and makes view.js an ES module.

⇄

render.php

data-wp-interactive="iapi-gallery"

Gives the engine a place to bind. It marks where the Interactivity API takes over, and it ties every directive underneath it to the iapi-gallery namespace.

// trimmed: the starter's render.php
<div <?php echo wp_kses_data( … ); ?>
  data-wp-interactive='iapi-gallery'
>
  <div class="slider-container">…</div>
  <div class="buttons">…</div>
</div>

If you miss the flag, the runtime never loads. If you miss the directive, it has nothing to bind to. You need both.

Section 4 · IAPI Primer · 0:31–0:39

What is the Interactivity API?

It's the standard way to add front-end interactivity to blocks, and it ships with Core.

  • Instead of every plugin bringing its own JS (and loading duplicates of it), everyone uses one pattern
  • It works for a simple toggle, and it scales up to live search, carts, and instant navigation
  • Directives are data-wp-* attributes that both the client and the server understand. That's what makes Section 7's no-flash first paint possible

Already running in Core

  • Search
  • Query Loop
  • Navigation
  • File
  • Image lightbox
Section 4 · IAPI Primer · ★ the mindset

Declarative, not imperative

// imperative: the HOW (plain JS, for comparison)
let current = 1;
nextButton.addEventListener( 'click', () => {
    current++;
    counter.textContent = current;
} );

You change the value, then you update the DOM yourself.

<!-- declarative: the WHAT (trimmed) -->
<button data-wp-on--click="actions.nextImage">
<p data-wp-text="context.currentSlide"></p>

// view.js
nextImage: () => {
    const ctx = getContext();
    ctx.currentSlide++;
},

You change the value. The directives keep the DOM in sync.

The state updates the UI, not the other way around.

You describe what the UI should be for a given state, never how to update the DOM step by step. That right-hand side is what you'll build in Section 5.

Section 4 · IAPI Primer · ★ the loop

The round-trip loop

directivereads the store
eventfires an action
actionmutates context
re-renderdirectives update
⟲ …and the directives read again

Every section from here is this loop with more parts.

You do the mutation and the runtime handles every re-render. That's the deal.

Section 4 · IAPI Primer

Anatomy of a directive

data-wp-bind--hidden---id

data-wp-

A standard HTML data-* attribute, so it's valid markup and the server can print it

bind

The directive name, which says what kind of relationship

--hidden

The parameter (two dashes), which says which event, attribute, or CSS property

---id

Optional unique ID (three dashes) that lets the same directive appear more than once on one element

The --parameter pattern works the same way for any event, attribute, or CSS property. Add ---id when you need the same one twice.

Today you'll use seven of them: wp-interactive, wp-context, wp-bind, wp-style, wp-text, wp-on, and wp-init. The rest are there when you need them.

Section 4 · IAPI Primer · ★ the distinction

Three kinds of data

Global state · belongs to all instances

// example, not in today's plugin
wp_interactivity_state(
    'iapi-gallery',
    array(
        'isLightboxOpen' => false,
    )
);
PHP · one value for every slider on the page

Local context · belongs to each instance

$context = array(
    'currentSlide' => 1,
    'totalSlides'  => 3,
);
…
<?php echo wp_interactivity_data_wp_context( $context ); ?>
<!-- outputs:
  data-wp-context='{"currentSlide":1,"totalSlides":3}' -->
render.php

Derived state · can be created from global state and context

state: {
    get imageIndex() {
        const ctx = getContext();
        return `${ ctx.currentSlide }/${ ctx.totalSlides }`;
    },
},
view.js

Global state belongs to all instances. Context belongs to each instance. Derived state can be created from both.

Section 6 · Sliding + Bounds · 0:49–0:59

Derived state

  • Disable logic is derived from currentSlide and totalSlides, so it lives in state, not context
  • Getters re-run on every read, so the UI stays in sync for free
  • A getter runs in the scope of the element reading it, so getContext() returns that slider's context, and one getter gives each slider its own answer
  • New directives: data-wp-style--transform, data-wp-bind--disabled
state: {
    get noPrevSlide() {
        const ctx = getContext();
        return ctx.currentSlide === 1;
    },
    get imageIndex() {
        const ctx = getContext();
        return `${ ctx.currentSlide }/${ ctx.totalSlides }`;
    },
    // + noNextSlide, currentPos
}

Section 7 · Server-Side Injection · 0:59–1:12

Count the slides with WP_HTML_Tag_Processor

The count is still hardcoded to 3. The render_block_iapi/gallery-slider filter gets the block's rendered HTML, so the Tag Processor can walk it and count the real slides.

Find the slider wrapper with next_tag()
Bookmark it with set_bookmark()
Walk the tags after it and count the slide blocks
Jump back to the wrapper with seek()
Write the real count with set_attribute()
// iapi-gallery-slider.php, trimmed
$slides = new WP_HTML_Tag_Processor( $block_content );

$slides->next_tag( array(
    'class_name' => 'wp-block-iapi-gallery-slider',
) );
$slides->set_bookmark( 'main' );

while ( $slides->next_tag() ) {
    // when class_list() contains a slide block's class:
    $total_slides++;
}

$slides->seek( 'main' );
$slides->set_attribute(
    'data-wp-context',
    wp_json_encode( $context )
);
return $slides->get_updated_html();

We do not set data-wp-interactive on inner blocks. Descendants inherit the wrapper's namespace. ★

The hydration flash

frame 1 · pre-hydration

‹   ›
counter: empty

frame 2 · hydrated

‹  1/4  ›
counter: filled

// the fix: seed derived state server-side, per slider
wp_interactivity_state(
    'iapi-gallery',
    array(
        'noPrevSlide' => function () {
            $ctx = wp_interactivity_get_context();
            return 1 === $ctx['currentSlide'];
        },
        'noNextSlide' => function () {
            $ctx = wp_interactivity_get_context();
            return $ctx['currentSlide'] === $ctx['totalSlides'];
        },
        'imageIndex'  => function () {
            $ctx = wp_interactivity_get_context();
            return "{$ctx['currentSlide']}/{$ctx['totalSlides']}";
        },
    )
);

Whatever you pass to wp_interactivity_state() has to match what the client getter computes on first paint. If they disagree, hydration visibly snaps the counter.

Section 8, now

  • data-wp-init fires when the element initializes. We add data-wp-init="callbacks.initSlideShow" to the wrapper in render.php
  • Returning a function from a callback is the cleanup registration, and it runs when the element leaves the DOM
  • Inside a callback you're in plain JS, so you can't look up actions.nextImage by name the way a directive does. Destructure store() to get real references

Section 8 · Autoplay

withScope in one slide

A requestAnimationFrame tick runs outside the Interactivity scope. Without the wrapper, getContext() and state are undefined.

Remember the speed string from Section 2? Convert it to a number before you multiply.

let start = null;
let rafId = null;
const update = withScope( ( timestamp ) => {
    if ( ! start ) {
        start = timestamp;
    }
    if ( timestamp - start > state.transitionsSpeed ) {
        actions.nextImage();
        start = null;
    }
    rafId = requestAnimationFrame( update );
} );

// the getter behind transitionsSpeed
get transitionsSpeed() {
    const ctx = getContext();
    return Number( ctx.speed ) * 1000;
},
